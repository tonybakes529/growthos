# Zapier: what is built, and what is left to do

Each client workspace connects **its own** Zapier account. Every Zap belongs to that account, runs on
that account's plan, and spends that account's task allowance. Growth OS holds no Zaps, sponsors no
tasks, and has no shared operator account to fall back on — there is deliberately no code path that
could reach one.

This file lists the configuration that still has to happen outside the codebase. It names environment
variables and never contains a value for any of them.

---

## 1. Why Connections currently says "Setup required"

Two prerequisites are outside the repository, and until both are met the Connect button is off and the
page says so rather than offering something that cannot work.

**a. The integration has to be registered with Zapier and published to their App Directory.**

Zapier issues OAuth client credentials for a *partner* integration, and the Workflow API — the one that
creates and switches on Zaps in a customer's account — is only available to a published integration.
A private or unpublished integration can be shared by invite link, and that is enough for a customer to
*build* Zaps by hand against our triggers, but it is not enough for the embedded "create the Zap for
them" experience. Publication is a review process on Zapier's side with its own requirements, and it is
the gate on the guided setup finishing a Zap end to end.

**b. Four environment variables have to be set on the deployment.**

| Variable | What it is | Where it comes from |
|---|---|---|
| `ZAPIER_CLIENT_ID` | OAuth client id for Growth OS as a Zapier API client | Zapier, once the integration exists |
| `ZAPIER_CLIENT_SECRET` | The matching secret | Zapier, same place |
| `ZAPIER_TOKEN_KEY` | 32 random bytes, base64, used to seal customer tokens at rest | Generated by us, see below |
| `SUPABASE_SERVICE_ROLE_KEY` | Already needed by the automations worker | Supabase project settings |

`NEXT_PUBLIC_APP_URL` is already set and is used to build the OAuth redirect and the `app_url` in every
event payload.

Generate the sealing key with:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Set it once and keep it. Rotating it makes every stored refresh token unreadable, which forces every
workspace to reconnect.

The redirect URI to register with Zapier is:

```
https://<your app host>/api/zapier/oauth/callback
```

Scopes requested: `profile zap zap:write zap:update zap:pause authentication connection:read`.

## 2. The Zapier integration to build

This is the app the customer adds *inside* Zapier. It authenticates to Growth OS with a workspace API
key, which the workspace issues for itself on the Connections page.

**Authentication:** API Key. One field, `api_key`. Sent as the `X-API-Key` header (a `Bearer` token or
an `api_key` query parameter are also accepted).

**Test endpoint:** `GET /api/zapier/me` → `{ workspace_id, workspace, slug }`. Use `workspace` as the
connection label so the customer can see which workspace a connection belongs to.

**Triggers** (REST Hook, one per event):

| Trigger | Event key |
|---|---|
| Student finishes onboarding | `customer.onboarding_completed` |
| Coach assigned to a student | `coach.assigned` |
| Student added to a course | `customer.invited` |
| Student created their login | `customer.registered` |

For each trigger:

- **subscribe** `POST /api/zapier/subscribe` with `{ "hookUrl": "<target>", "event": "<event key>", "zap_id": "<optional>" }` → `201 { id }`
- **unsubscribe** `POST` or `DELETE /api/zapier/unsubscribe` with `{ "id": "<the id subscribe returned>" }`
- **perform_list** `GET /api/zapier/triggers/<event key>` → the ten most recent real events of that type
  for that workspace, in the same shape as a live delivery, so field mapping in the Zap editor works
  against real data

Every payload carries `id` (`evt_<n>`), `event`, `occurred_at`, `workspace_id`, `entity_type`,
`entity_id`, `app_url`, and the event's own fields. `id` is stable across retries, which is what Zapier
deduplicates on.

`automation_trigger_types` in the database is the list of events that may be subscribed to; anything
else is refused with a 404.

## 3. Deployment

The delivery worker runs inside the existing events cron, so there is nothing new to schedule:

```
/api/cron/events   – every minute: automations, delayed steps, email outbox, Zapier delivery
```

It needs `CRON_SECRET` and `SUPABASE_SERVICE_ROLE_KEY`, both of which it already needed.

Delivery is an outbox: `private.enqueue_zapier_deliveries` turns committed `domain_events` into one row
per active subscription, `private.claim_zapier_deliveries` takes a batch with `for update skip locked`,
and `private.settle_zapier_delivery` records the result. A failure is retried with exponential backoff
(2, 4, 8… minutes) and given up after six attempts; a `410 Gone` from Zapier drops the delivery and
switches the subscription off, which is the REST Hook contract.

## 4. What a workspace does, once the above is done

1. **Manage → Connections → Connect Zapier.** They authorise their own Zapier account. The tokens are
   sealed with AES-256-GCM before they touch the database, and the table holding them has row level
   security on with no policy at all, so no signed-in user can read it through the API under any role.
2. **Issue a key.** Shown once, stored only as a SHA-256 hash.
3. **In Zapier**, add Growth OS, paste the key, and authorise Slack or Google Calendar *there* — that is
   where those tokens live, and it is why the Connections page treats "Zapier connected" and "Slack
   authorised" as two separate facts and never infers one from the other.
4. **Switch the Zap on.** That is what makes Zapier call subscribe, and it is the only thing that makes
   an automation live. The Connections page reports a Zap as listening only when Zapier has told us so.

## 5. Limits worth knowing before promising anything

- **Delivery is not execution.** Growth OS can prove it handed an event to Zapier and that Zapier
  accepted it. Whether Slack posted is in the customer's own Zap history. The delivery log says exactly
  this, and nothing in the UI upgrades "delivered" into "sent".
- **The embedded experience depends on publication.** Until the integration is published, the guided
  setup records a configuration and says plainly that it has not switched anything on. It does not
  pretend to have created a Zap.
- **Task → Google Calendar is marked unavailable, with the reason shown on the card.** `public.tasks`
  holds `title`, `description` and `due_at` — no end time and no timezone — so a calendar entry could
  only be produced by inventing an end and guessing a timezone. `coaching_sessions` does carry
  `scheduled_start`, `scheduled_end` and `external_event_id`, so this template becomes honest as soon as
  sessions are wired up as a trigger.
- **Disconnecting cannot delete the customer's Zaps.** They are in the customer's account. Disconnect
  stops delivery and forgets our tokens; the Zaps stay and stop receiving events. The page says so.
